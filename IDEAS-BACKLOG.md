## A. Brand

1. **Voice** — idea. Two candidates: third-person brand-as-actor ("Trilorah does this for you") vs. first-person-plural ("We bring intelligence and beauty to your Sunday service"). Leaning **we**.
   Decision: **"We"** in marketing/onboarding; plain imperative (no pronoun) on live surfaces; never "I". (2026-09-05)
2. **Personality** — decided: **calm, competent, reverent.** No jokes, no exclamation marks, no gamification.
3. **Positioning** — decided: "the intelligent projection assistant for churches." Wins on hearing the sermon and putting the verse up itself, not on feature parity with ProPresenter.
4. **Experience principles** — undefined.
5. **Taglines** — idea. "Beautiful, effortless, intelligent" (already the motto). New candidate: **"Built to serve the service."**

## B. Navigation & search

6. **Semantic in-app search** — not built. Every page/component has a pinpointable route + anchor. Search understands intent ("how do I get to the PostHog dashboard?") not just keywords, and clicking a result navigates straight to the element. Reference: Vercel docs' AI search. Open question: LLM or just good embeddings? User's note: **lightweight, accurate, fast vector embeddings.**
   Decision (2026-09-05): Raycast-style popup (Cmd+K + sidebar icon), on brand. No runtime LLM: a **command registry** (id, route+anchor, title, "how a person would ask" paragraph) embedded at build time with a small local sentence model (MiniLM-class via ONNX in main), blended with fuzzy keyword score. Result click navigates, scrolls to anchor, pulses a highlight ring. **Actions included** ("Go live", "Switch to KJV") but rendered as a different-colour row and require **Shift+Enter** to run, never plain Enter. **Content (songs, presentations, verses) excluded** — they keep their own typeahead.

## C. Companion (QR) experience

7. **Share button** — not built. Anyone with the companion link can share it (WhatsApp share sheet / copy link / QR). Use case: family member at home streams the service.
   Decision (2026-09-05): Share open by default via native share sheet (copy link + QR fallback on desktop). Church-level toggle: "Anyone with the link" vs "Church Wi-Fi only" (hides share button). **Stable per-church slug**, not per-service code. Late joiners get replay buffer. **Link keeps working after service** as a take-home recap page (later).
8. **Audio stream on companion** — idea. Companion could carry live audio, not just transcript + verses. (Bandwidth/cost implications — see QR brainstorm's relay cost notes.)
   Decision (2026-09-05): **No audio.** Egress + media server cost breaks the free/local model; YouTube/Facebook Live already cover it. Instead: church settings gets a "stream URL" field; companion page shows a "Watch the stream" button linking to it. Audio via WebRTC only ever as a paid-tier idea.
9. **Viewer count + geography** — not built. Operator dashboard shows how many are connected via QR, in-venue vs. remote, and where remote viewers are (city-level, not a map necessarily).
   Decision (2026-09-05): Live "N watching" pill on Live surface next to QR button (relay socket count). In-venue = same public IP as church laptop; else remote. City-level via offline IP DB (GeoLite), **no phone location**. Short list not a map; aggregate only, small numbers rounded. Breakdown + peak/avg watch time go on post-service recap / web dashboard, not on Live.
10. **Congregation as training signal** — idea. When detection confidence is low (e.g. 61%), companion viewers get a light prompt: "Did the preacher say John 1:1 or Gen 1:1?" Lighter than operator prompts but heavier than passive. Do NOT prompt when confidence is high.
   Decision (2026-09-05): Yes. Flow: (1) laptop emits `poll` when top score is 40–75% and a 2nd candidate >15%; poll id, 2–3 candidates, 45s expiry. (2) phone shows one quiet card ("Did you hear John 1:1 or Genesis 1:1?"); max one per 3 min, skip if viewer ignored last two; no gamification. (3) `vote` event upstream with anonymous per-session id, one vote each. (4) laptop tallies: in-venue weight 1.0, remote 0.5; bounded score adjustment (~15 pts max), can reorder but never invent a candidate. (5) operator prompt updates live ("18 heard this"); operator still approves. In auto mode votes only break a tie. (6) on resolution: poll closes, card dismissed, example written to preacher profile with operator choice as label, tally as a low-weight feature. (7) store aggregates only; individual votes discarded; participation count on recap.

## D. Operator experience

11. **Screen-edge glow notification** — not built. iOS-Siri-style gradient glow around the whole window when a verse is detected and needs approval. "Visual vibration" — the operator feels it wherever they are in the app. Ping sound when in auto mode.
   Decision (2026-09-05): New foundation primitive **EdgeGlow** (beside Toast C-63). Reference: the `border-beam` look from libraries.dev/beam (soft gradient riding the border, blurred outward) — **reimplemented in pure CSS, no package**: fixed pointer-events-none layer, conic-gradient masked to the window edge, animate only opacity + gradient rotation (compositor-only). Three signals only: verse awaiting approval = brand accent, breathing ~4s; auto-pushed = single soft pulse + ping; fault (mic/projector lost) = warm red, steady. Enter 220ms, dismiss 140ms, reduced-motion = static border. Never on the projector output window. Ping only in auto mode, volume setting, off by default. Toast stays for non-live events.
12. **Folders in Presentations / Songs / Media** — not built. Folders in a first horizontal row (with "see more"), un-foldered files below, collapsible.
   Decision (2026-09-05): One shared **Library layout** for Presentations/Songs/Media. Top strip of folder cards (first ~6 + "See all" expands to wrapped grid); "Everything else" section below; both collapsible, state remembered per screen. **Flat, one level, one folder per item.** Folder card: name, count, up to 3 stacked thumbs; rename/colour/delete via ActionMenu; deleting folder never deletes items. Folders are index metadata, not disk directories (paths stay stable). Drag item → folder to move; drag folder to reorder (ArrangeList). In-screen search ignores folders, shows folder as breadcrumb on results. Tags maybe later for cross-cutting labels.
13. **Seasonal component skins** — idea. Icons wear a Christmas hat etc.; respect the church's timezone/holidays.
   Decision (2026-09-05): Yes, **after core UI is done.** Sidebar app icon, empty states, loading orb only — never Live surface, projector, or functional icons. Christian calendar first (Advent/Christmas, Lent/Easter, Pentecost; computed dates), then civic holidays by church country; data-driven config. Thin layer: accent shift + SVG overlays, not a theme swap. Settings switch "Seasonal touches", on by default.
14. **Generated avatars, no uploads** — not built. No image storage (free tier, no storage cost). Generate per-user/per-church art: Vercel-style gradients, or JSON/generative art seeded by the church's brand colour. 
   Decision (2026-09-06): **Preachers/operators: generative**, deterministic gradient from name hash + initials (C-45), no storage. Church settings picks one **brand colour** that seeds every avatar in that church. **Church logo is the exception**: real image, lives on the church laptop only (transport bar logo action, sidebar); relay caches one ≤200KB copy per church for companion/recap page. Later: extract dominant logo colours as the seed.

## E. Preacher profiles, training, auto mode

15. **Know when to stop training** — **mostly built** (`correctionLedger.ts`: training thermostat, Wilson-bound trust floor, matures → prompts off, accuracy dip reopens).
   Decision (2026-09-06): Keep. Add one line on PreacherCard: "Training complete, prompts off since N services". System detects when a preacher's profile is confident enough and stops showing training prompts.
16. **Auto mode** — **partly built** (eligibility gate 90% trust / 100 samples / 5 services; auto-push on reading-started or immediately; **no operator opt-in switch, no clash concept, no ping**).
   Decision (2026-09-06): (a) Auto mode becomes a **per-preacher operator switch**, enabled only when eligible; eligibility alone must not flip behaviour. (b) Resolver surfaces a **second candidate + score**; in auto mode, top-two within ~15 pts = **clash** → hold, EdgeGlow, ask operator. Same candidate data feeds congregation voting (item 10). (c) Ping on auto-push (EdgeGlow spec). (d) Drop "600 in a row"; the Wilson trust floor already covers it. If a preacher is consistently correct (e.g. 600 in a row, clean accent), operator can enable auto: verses go straight to screen. Only interrupt the operator on a **clash** (two candidate verses). Ping sound on auto-push.
17. **Voice commands from the preacher** — **mostly built** (`voiceCommands.ts` + `commandConfig.ts`: version switch, verse corrections, prayer suppression, take down/leave up; phrases are config incl. language packs + user json).
   Finding: `navNext`/`navPrevious` phrase lists exist in `commandConfig.ts` but the engine never fires them. Defaults ("next", "back", "continue", "before") are too generic — would trigger on ordinary speech.
   Decision (2026-09-06): (a) Wire nav-next / nav-previous in the engine, with **safe defaults only** ("next verse", "previous verse", "go back a verse", "verse before"); single words stay out of the default list. (b) **Per-preacher command phrases**: a 4th config layer, `<preacher>/commands.json`, unioned on top of the user file when that preacher is active. (c) **Operator teaches phrases in the Preacher profile**: a "How they say it" panel with one row per command (hold, next, previous, take down, version) where the operator adds the preacher's own wording ("hold that", "let's move", "go up one"). (d) **Learn from the log**: every detected command is logged as an event (utterance, kind, preacher, ts, whether the operator undid it within 10s). Undone commands become false-positive examples; utterances the operator manually mapped after a miss become new phrases. Log panel visible in the profile. (e) Shared phrases stay in the user file; nothing preacher-specific leaks into defaults. Natural-language control during preaching: "next verse", "I said verse 4", "take that down". System recognises, executes, and **logs** every detected command. Open question: need training data of how preachers actually phrase these?
18. **"Auto-correct for the pastor suffix like the scripture one"** — unclear. A note from someone else ("bro"). Best guess: auto-correct transcript misspellings of the pastor's name/title the same way scripture references get normalised. To clarify.
   Decision (2026-09-06, provisional): Two readings. **(1) Name/title auto-correct** — ASR mangles proper nouns; each preacher profile gets a small **vocabulary list** (name, title, church name, common names in the congregation) used for ASR keyword boosting where the provider supports it and for post-transcript replace otherwise. Applies to transcript, notes, companion page, recap. **(2) Reference-suffix habits** — some preachers append a habitual tail after a reference ("…Amen?", "…say verse ten", "…in the NIV") that confuses the resolver; the per-preacher command layer (item 17) already covers version suffixes, add a per-preacher "ignore tail phrases" list. Build (1); (2) is a tiny addition. Confirm with the original author which was meant.

## F. Multilingual & ML

19. **How much ML is needed for accent-accurate training?** — question. Accents incl. Nigerian, French-influenced English. Is per-preacher fine-tuning needed or is adaptation (bias/keyword boosting + few-shot) enough?
   Decision (2026-09-06): **No per-preacher model training.** Three cheap layers instead: (1) ASR: multilingual Whisper (small/medium) already handles West African & French-accented English far better than base.en; add per-preacher vocabulary/keyword boost (item 18). (2) Resolver: it's rule-based + ledger; accent errors show up as book-name misses, so each preacher profile accumulates an **alias map** ("gee-oh-nah"→Jonah) from corrections — that IS the per-preacher training, and it already lives in the correction ledger. (3) Priors: seasonal priors + recent-chapter context already exist. Only if data later shows a plateau: fine-tune a small Whisper on that church's corrected audio, opt-in, paid tier. Note: `mlClient.ts` points at a resolver on :8765 that does not exist in the repo (`ml/` is empty) — dead path, remove or document.
20. **Five extra languages** — idea. Full parity per language: scripture DB, translations, training data, constraints, UI. English stays primary. Cost/effort estimate needed.
   Finding: es/fr/pt/hi/zh **language packs already exist** (book aliases, spoken numbers, commands). Bible DB has RVR (es), APEE (fr), AA (pt), CUV (zh) — **no Hindi text**. Whisper multilingual model already selected when asrLanguage ≠ en.
   Decision (2026-09-06): Languages are ~70% done at engine level. Per-language checklist to reach parity: ① scripture text (Hindi missing; verify public-domain sources), ② language pack QA with a native speaker, ③ UI strings (none localised yet), ④ Whisper `small` not `base` for non-English, ⑤ per-language false-positive filter tuning. Effort: ~1–2 weeks per language for one person, mostly QA and data, not ML. Ship order: es, fr, pt (Bible present), then zh, then hi once a Bible text is found. Do it **after** the English UI rebuild.
21. **LibreTranslate** — question. Does it help for live translation on the companion page?
   Decision (2026-09-06): **Not for scripture — never.** Verses come from the translation table by reference, so a Spanish viewer gets RVR text, not machine-translated KJV. LibreTranslate is only relevant for translating the **live transcript/notes** on the companion page. It's self-hostable and free but quality is mediocre and it adds a server. Defer; if ever, run it on the relay for transcript only, clearly labelled "machine translated".

## G. Mobile / remote control

22. **Operator remote app** — idea. For solo preachers / small bible studies: control scripture display from a phone over LAN while the laptop drives the projector. Scope: scripture controls + auto controls only. NOT for congregation, NOT for configuration. App vs. web page undecided.
   Finding: `integrations/websocketServer.ts` already accepts inbound actions on :8081 (START/STOP_LISTENING, CLEAR_SCREEN, PUSH_PREVIEW, SET_MODE) with **no auth**.
   Decision (2026-09-06): **Web page, not an app.** Laptop serves `/remote` on the LAN; operator opens it via a QR in Settings → Remote; phone adds it to home screen (PWA). Scope v1: approve/dismiss the pending verse, next/previous verse, clear/black/logo, listen on/off, auto mode toggle, type a reference. Nothing else, no settings. **Pairing**: 6-digit code shown on the laptop, exchanged once for a token stored on the phone; the socket rejects unpaired clients (fixes the open-port issue too). Reuses the existing WS action handler + the companion page's event stream. Works offline on church Wi-Fi; if no Wi-Fi, laptop hotspot is the documented fallback.

## H. Infra & content

23. **CCLI lyrics API / song DB** — idea. Songs screen today = local lyrics library, manual paste.
   Decision (2026-09-06): **Not now.** CCLI SongSelect has no public API; access is a partner agreement, churches must hold their own SongSelect licence, and lyrics are copyrighted (can't be bundled or cached on our side). Instead: ① keep paste/import; ② add **SongSelect ChordPro / .txt import** (files a licensed church can already download); ③ a "CCLI number" field per song so reporting is easy; ④ OpenLyrics XML import for churches moving from OpenLP/EasyWorship. Revisit a partner API only when there's a paid tier to justify it.
24. **Kubernetes** — unrealistic-for-now.
   Decision (2026-09-06): **No.** The app is a desktop binary; the only server is the relay, which is one small Node process. Fly.io / Render / a single VPS with a Dockerfile. Kubernetes becomes a question only past thousands of concurrent churches.
25. **Evals** — partly built: 5 vitest suites (resolver, intent, voice commands, multilingual, seasonal priors) = unit tests, not evals. No recorded-sermon fixtures.
   Decision (2026-09-06): Build an **eval harness** on top of vitest: ① a fixtures folder of real transcript segments (anonymised) with expected references, grown from every operator correction (ledger already has the pairs) — opt-in export from the app; ② metrics per run: precision, recall, false-positive rate, median latency, per-preacher and per-language breakdown; ③ a threshold gate in CI so a resolver change that drops recall fails; ④ later, audio-level evals (Whisper model × accent) using the same fixtures with audio. This is what makes "600 in a row" a measured claim instead of a feeling.

26. **Online services: stream output + virtual camera** — idea (2026-09-17). Let Trilorah feed Zoom / Google Meet / Teams / StreamYard / OBS, operator still in control. Two audiences: hybrid churches that already stream, and **fully online churches** (no room, no projector; the stream is the sanctuary). Strongest fit: the **solo pastor on a webcam** with nobody running slides, where verse-following does the operator's job.
   Finding: nothing "joins" a meeting. Meeting bots (Zoom Meeting SDK, Recall.ai) are heavy, paid per hour, and Meet has no supported bot API — **rejected**. Screen-sharing the output window already works today with zero code.
   Decision (2026-09-17, provisional — **later**, after the UI rebuild): three steps, in order.
   ① **"Stream" output role + localhost overlay page** (a few days). A lower-third rendering of the live verse, transparent background, served over the existing websocket server. OBS / vMix / StreamYard add it as a Browser Source. Full slide stays on the projector; the stream gets the overlay. Ship with an "OBS Virtual Camera" setup guide so Zoom/Meet users are covered without drivers.
   ② **Windows virtual camera** (~1–2 weeks; must be built and tested on Windows). Offscreen-rendered output window at 1280×720 @ 30fps → N-API addon → shared memory → DirectShow filter registered at install (admin once). Build on **Softcam (MIT)**; OBS's virtualcam is **GPL — do not copy**. Media Foundation virtual camera is Windows 11 only, so not sufficient alone.
   ③ **macOS Camera Extension** (~2–4 weeks). CoreMediaIO system extension in Swift, bundled in the app. Needs paid Apple Developer account, system-extension entitlement, Developer ID signing, notarization, app in /Applications, one-time user approval in System Settings. Extension is sandboxed in its own process, so frames go in through a sink stream, not plain shared memory.
   Gotchas to design for: **no audio** over a virtual camera (mic goes to Zoom directly; lyric-video sound needs "share computer sound" or a virtual audio cable) · Zoom/Meet compress camera video to 720p so **verse type must be large and high-contrast** · Zoom **mirrors the presenter's own preview** (attendees see it correctly — say so in the UI).
   Open question for the owner: is Trilorah a **verse layer** on top of OBS/StreamYard (cheap, step ①), or the **whole studio** for a solo pastor — webcam in, verse composited, virtual camera out (a different app surface from the projector one; needs its own brainstorm)?
