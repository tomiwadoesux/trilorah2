# Desktop privacy evidence

Internal drafting evidence, reviewed October 17, 2026. This is a source audit of the current working tree, not a verified release or provider configuration audit. No production accounts, databases, `.env` values, embedded credentials or personal user files were accessed. References below are repository-relative file paths and source line numbers at review time. The separate cloud audit owns `electron/cloud/*`, the website, Supabase schema and public companion access rules.

## Material findings for the policy draft

- **Speech recognition defaults to local Whisper.** `electron/data/settings.ts:88–92` sets `asrProvider: 'whisper-local'`. `electron/asr/provider.ts:57–67` uses Deepgram only for an explicit Deepgram selection with a configured key; missing keys fall back to local Whisper. This supports a claim about the speech recognizer, not an all-app local-only guarantee.
- **Generated notes are cloud processing, including the option labelled local.** `electron/llm/notesProvider.ts:54–62` always delegates `localNotesProvider.generate` to `cloudNotesProvider.generate`, even if the optional local dependency exists. Its `status()` can nevertheless return `ready (on-device)` at line 52. Do not promise local notes generation or that selecting local notes keeps the transcript off cloud services.
- **Start Listening can also start public cloud sharing for a signed-in, configured church.** `electron/main.ts:2146–2174` calls `ensureCloudService()` after starting a real microphone; the cloud audit covers the authentication conditions, public defaults, payloads, retention and access. Stopping recognition does not itself end cloud sharing (`main.ts:2210–2219`).
- **Phone microphone pairing is internet-assisted.** Supabase carries signaling; Google STUN is configured. Audio is transported through a WebRTC peer connection, then fed into whichever ASR provider is selected. It is inaccurate to turn “peer-to-peer audio” into “nothing goes online.”
- **Exports can contain sermon words and named preacher records.** The `.tri` content selection can include current transcript, notes, local service records, preacher profiles, teaching/correction records, vocabulary, command configuration and command logs. Sharing a package is a separate disclosure by the person who saves/shares it.
- **Deleting a preacher is not a universal erasure operation.** The UI handler removes profile, ledger, teaching and training files; vocabulary, command configuration and command logs are not part of that handler. Existing exports, cloud rows and console records are separate copies.

## Generated notes and optional language-model analysis

- `electron/main.ts:3257–3264` obtains accumulated sermon text and calls the selected notes provider when `generate-sermon-notes` is invoked. The current dashboard provides an explicit Generate action (`src/design/screens/dashboard/SermonNotesTile.tsx:63–74`); generation is not established as an automatic consequence of every normal listening start.
- `electron/notes/sermonNotesGenerator.ts:40–78` requires an HF token and posts a prompt containing up to the first 6,000 characters of sermon transcript to `https://api-inference.huggingface.co/models/meta-llama/Meta-Llama-3.1-8B-Instruct`. Response processing extracts title, theme, main points, definitions, applications, quotations and summary. This names the configured HTTP recipient/model; successful current endpoint operation was not tested.
- `electron/data/settings.ts:45` defaults `slowPathEnabled` to false. If enabled at startup, `electron/main.ts:4196–4247` creates and starts a background reasoning loop. `main.ts:1484–1490` enqueues speech chunks. `electron/llm/reasoningLoop.ts:48–74` and `reasoningPrompts.ts:44–70` construct a request including new speech, recent transcript, service segment, recent/active references, expected sermon-plan references, earlier context and any tool observations.
- `electron/llm/llmFallback.ts:26–65` requires an HF token and sends those prompts to the same HF inference endpoint. Separate disambiguation/loose-reference helpers at `:75–185` can send transcript/candidate-reference prompts if called. Their existence alone does not prove that every listening session calls those helpers.
- `electron/llm/notesProvider.ts:27–35` considers cloud notes available when a token is configured. `:38–63` calls the supposedly local choice experimental but delegates to cloud. No local summarizer runs here.
- The source does not establish HF/provider request retention, model training use, downstream inference routing, region or actual account settings. Do not promise zero retention, no training use or that every “local” setting prevents these calls.

## Phone microphone

- `electron/mic/phoneMicLink.ts:72–106` makes a temporary code/HTTPS page URL, waits for one phone and asks the desktop operator to approve it. `:164–190` expires pending pairing or tears down a call/code.
- `phoneMicLink.ts:200–225` uses a public Supabase Realtime broadcast channel whose name contains the random pairing code. Messages contain phone/laptop names, phone ID, offer/answer SDP and ICE candidates. The code and approval reduce accidental access; they are not a claim that signaling is end-to-end encrypted or inaccessible to the signaling service. Supabase retention/logging/access configuration is unverified.
- `src/lib/phoneMic.ts:91–125` creates a WebRTC peer with `stun:stun.l.google.com:19302` and exchanges candidates/SDP over the bridge. This can disclose connection metadata (such as IP/candidate details) to peers/signaling/STUN infrastructure. No TURN relay is configured in this desktop source.
- The audio stream arrives on the renderer peer (`phoneMic.ts:99–108`), then `micCapture` routes it to the selected local/cloud recognizer. A `words` data channel also returns transcript lines and caught/live scripture references to the paired phone (`phoneMic.ts:24–49`).
- `phoneMic.ts:57–67` stops tracks and closes the peer when disconnected. The audited desktop path does not save a dedicated phone audio recording. Actual ICE routing, third-party network logs and release microphone permission behavior remain runtime/provider checks.

## Local mobile remote and integration control

- `electron/integrations/mobileServer.ts:35–43` starts an HTTP server on `0.0.0.0`, normally port 8082, and displays local interface addresses. Requests are not TLS encrypted by this server. Calling it “private LAN” describes intended use; it does not itself restrict reachability beyond the actual network/firewall.
- Pairing checks a temporary six-digit code, then requires desktop approval (`mobileServer.ts:73–93`). Pairing attempts track requesting IP in memory for a short rate-limit period (`:74–77`, `:31–33`). Paired requests use bearer tokens (`:95–104`).
- `electron/integrations/pairing.ts:54–96`, `:99–126`, `:140–145` save device names, IDs, random tokens and paired/last-seen times as JSON in `remote-pairing.json`; the operator can revoke devices or all devices. Mobile HTTP pairing has its own store rooted under `userData/mobile` (`electron/main.ts:131–148`).
- `public/mobile-remote.html:734–745`, `:1382–1385`, `:1492–1497` save the phone token in browser localStorage; local Disconnect clears that browser token. Desktop revoke is the way to invalidate its access centrally.
- `src/design/screens/useMobileRemote.ts:85–113` sends paired remote state/library responses: live and preview text, scripture suggestions, song titles/lyrics/sections, media/deck labels, run order, timers and sharing/listening status. The remote can request current thumbnails (`:99–103`) and send supported control/edit actions. This is access to meaningful church content, not only a generic remote button.
- The separate WebSocket integration server uses `new WebSocketServer({ port })`, normally 8081, without TLS or explicit host restriction (`electron/integrations/websocketServer.ts:82–97`). It authenticates a token or redeems a pairing code (`:187–219`). Do not describe its console `ws://localhost` string as proof that it binds only to localhost.

## Export, deletion and logs

- Notes export uses a user-selected save location for PDF/Markdown (`electron/main.ts:3267–3288`; `electron/notes/sermonNotesGenerator.ts:109–118`, `:192` onward). These are user-managed files, separate from app memory and cloud data.
- `.tri` saves selected categories to a user-picked file, initially suggesting Documents/Trilorah/Services (`electron/packages/triIpc.ts:84–104`). `electron/packages/triCatalog.ts:19–36`, `:119–128`, `:139–186` can include church/giving details, run, songs, media, presentations, preacher profile and related learning records, service logs and extra records. `electron/main.ts:3992–3997` supplies current transcript and notes. The export uses allowlisted appearance/church/tool fields rather than all settings; provider credentials are not among those allowlists.
- `electron/preachers/evalExport.ts:93–108` hashes preacher IDs when the optional local evaluation export is requested, but leaves the heard transcript words unchanged. `electron/main.ts:2432–2436` writes local `eval-fixtures.jsonl`. Hashing an ID does not establish anonymous text; names or identifying statements can remain in the words. No automatic upload from this export function was found.
- `electron/main.ts:3419–3425` deletes the named profile plus ledger, teaching and training files, and clears the active preacher selection. It does **not** call removal for vocabulary, per-preacher command files or command logs. Do not claim it erases all preacher-related data, cloud copies or exported packages.
- Song deletion is wired at `main.ts:2428`; presentation deletion removes generated files at `main.ts:3122–3142`. These targeted paths do not establish a global “delete all data” UI or account deletion. No universal all-data erase path was found in the audited desktop scope.
- Console output includes speech and manual text (`deepgram.ts:127`, `whisperLocal.ts:333`, `main.ts:1426`, `:2107`), alert text (`main.ts:418`), preacher names and file paths. A production file-based console/crash-log collection backend was not established in this audit. Therefore do not promise “no logs,” and do not claim automatic diagnostic upload. If users send logs/support bundles, advise redaction of sermon/personal/credential material in the support workflow.
- `electron/data/aliasLogger.ts:7–18` creates a logs directory/path but does not append alias content in its current implementation; its filename alone is not proof of collected miss records.

## Statements to avoid and release checks

Avoid “everything stays on your computer,” “we never receive sermon text,” “local mode never goes online,” “local notes run on device,” “delete profile deletes all its data,” “anonymised export contains no personal data,” or “audio is never saved to disk.” The evidence above either contradicts them or does not establish them.

Before publishing a policy or setup guide, verify the actual release's default settings, provider endpoint operation/terms, compiled service configuration and ownership, provider retention/training arrangements, public-sharing consent/disclosure, local file locations, complete deletion/export instructions, security update distribution and available support inboxes. No retention deadline, data-center region, encryption-at-rest promise, privacy-rights response time or provider training exclusion can be derived from these desktop files alone.
